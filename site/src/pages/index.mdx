The question this sweep was built to answer is narrow: if a serving stack picks one attention implementation on the hardware it was tuned on, how much does that choice cost on a different part, and can the measurement even tell.

## Implementation provenance

Splitting authored code from integrated code matters here, because a fair share of this result is a statement about library builds rather than about kernels written for this study.

Written for this project: the PyTorch reference (`P0-naive`, `D0-naive-kv`), which materialises the score matrix and exists as a correctness anchor rather than a contender; the `torch.compile` variants (`P1-inductor` with its `nofuse` and `where` spellings, and `D1-inductor`), which are compilation configurations of that reference; the SDPA call sites (`P2b-sdpa-mem-eff`, `P2c-sdpa-flash`, `P2d-sdpa-cudnn`, `D2-sdpa`), which force one PyTorch backend each and therefore measure the backend PyTorch dispatches into rather than code written here; and `P3-triton`, a Triton attention kernel carrying a local BF16 modification made for this sweep.

Integrated and measured, not authored: `P4-fa2`, `P4h-fa3`, `D3-fa-kvcache`, `D6-fa-prefill-at-1` and `D4-flashinfer` are calls into prebuilt CUDA libraries, flash-attn {web.software.flash_attn} and FlashInfer {web.software.flashinfer}. Nothing inside those paths was modified. Where one of them wins, the finding is about that library build on that device at this software snapshot, and it does not transfer to another version of the same library.

One layout caveat applies to the FlashInfer comparison throughout. The page size in every decode cell equals the KV length by construction, so the FlashInfer and FlashAttention decode entries differ by library, not by KV layout. No page-size sweep was run, and no number here can be read as a cost of one layout against another.

## Validity before performance

A latency table is worth nothing if the row did not run the kernel it claims. Three checks come before any timing comparison: what ran, what dispatched, and whether the output was right.

Outcomes are four distinct things and are kept apart. `OK` is a clean timed row. `UNSUPPORTED` means the implementation declined the configuration by design, for example FlashAttention-3 on pre-Hopper parts. `OOM_PREDICTED` means the allocation was computed in advance to exceed memory and the cell was skipped without running. `OOM` means an allocation was attempted and actually failed. Collapsing these into one failure surface would read as instability where most of it is a documented refusal.

## Decode and the KV cache

Single-token decode does very little arithmetic and moves the whole cache, so the useful model is bytes rather than FLOPs. The cache traffic for one decode step is

$$
\text{bytes} \;=\; 2 \, B \, H_{kv} \, N \, D \, s
$$

with $B$ the batch, $H_{kv}$ the number of KV heads, $N$ the KV length, $D$ the head dimension, $s$ the bytes per element (2 for bf16), and the leading factor 2 counting the K and V tensors. The effective bandwidth below is that analytic byte count divided by measured time. It is a model rather than a profiler reading, and the byte model differs between implementations, so effective bandwidth compares one implementation against itself across shapes far more safely than it compares two implementations at one shape.

Every decode comparison across devices in this section is confounded. The A10 and A100 decode rows were collected under a different commit and driver than the H100 and L40 rows, so a panel-to-panel change mixes hardware with software provenance and cannot be attributed to architecture alone. Prefill has no such split.
